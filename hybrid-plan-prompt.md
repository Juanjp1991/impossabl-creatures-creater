## 4. The two versions I've built, and the trade-off

### Version A — LLM writes raw SVG path data (this is what the repo runs today)

The model receives a style guide and anatomy plan, then emits raw `<path>` data for all five parts, targeting fixed anchors in five local coordinate systems.

- **Worked: species likeness was good.** Animals were recognizable — the trunk, the beak, the mane.
- **Failed:** unpredictable. Seams didn't close, limbs floated, anchors were missed, style drifted, quality decayed across long output. It needed a validate → LLM-review → repair loop, and that loop often made things worse.

### Version B — fully parametric

Geometry in TypeScript; the model output only JSON parameters plus a palette. Predictable, tiny, error-free — but the animals were generic quadrupeds, unrecognizable. (Vestiges of this survive as the hardcoded placeholder art in `game/src/library.ts`.)

### Diagnosis — challenge this if you disagree

Species recognizability lives in idiosyncratic features that don't fit a shared parameter space — a trunk, antlers, a hump, a beak. **Structural correctness from code, likeness from the model.** Version A's generation approach was right; its lack of enforcement was wrong, and enforcement now exists.

But the repo's history shows a *second* failure mode I only now recognise: **LLM-judged-against-LLM conformance.** The blueprint checks grade the generator against the planner's invented numbers; the review/repair loop grades one model call against another's opinion and "fixes" accordingly. Both manufacture errors and burn minutes without a deterministic ground truth. Stage 1 keeps every check whose ground truth is *physical* (parses, bounds, seam pixels, ground line, node counts, palette tokens) and deletes checks whose ground truth is *another model's output*. Do not propose replacing raw-SVG generation. Alternative architectures belong in Stage 2 (section 7).

### 5.1 Deterministic structural enforcement — mostly built; resolve four contradictions

The enforcement exists. But my original principles are **contradicted by the shipped code**, and the plan I wrote before never noticed. Give me a decision on each, with a recommendation:

### 5.2 A single global canonical standard — the biggest genuine gap

This is the thing I most want, and the current repo does **not** have it. `src/generation/styleGuide.ts` is *prose* ("approved-bear-cheetah-2.0.0"), and the validator never checks a global stroke weight or detail density. My earlier draft scored each part relative to its own animal — wrong, because the whole game is cross-species mixing. Fifty internally-consistent animals combine worse than fifty conforming to one shared standard.

Define **one canonical reference for the whole roster** as **hard constants checked in `validateAnimalDraft`**, not prose:

- **one fixed stroke-weight constant.** The good tiger example already converges on this: each of its five root groups inherits `stroke-width="3"` for the silhouette outline, and its only detail stroke is a `1.2` in the head. **Decided constants: silhouette outline = 3; internal detail 1–1.5; strokes under 1 banned** (they disappear on a cheap 360px-wide screen); reject any `stroke-width` outside those beyond a small tolerance.
- **one shared silhouette scale.** The failed hippo proves this is unenforced: the normalizer silently rescued its five parts at scales of **0.19–0.62 — a 3.2× spread within a single animal.** But note the right metric: under snap-always, "authored scale" is the wrong thing to gate, because the global-canvas rescue path legitimately rescales. Enforce it instead as a **post-normalization fill-ratio band per part**: each part's occupied bounds (already computed by `analyzeDraftGeometry`) must fill a fixed fraction of its fixed local view — the fixed views (`PART_CONFIG`: 160×160, 300×220, 260×180) *are* the shared "unit of shoulder height," so a fill band makes every species' body the same order of size by construction. **Decided band, mined from the tiger: occupied height 65–95% of the part view's height** (tiger measures 72–92% across its five parts). Gate on height only — width-fill is structurally low for leg sets, which sit near their anchor inside the wide 260px view. Reject (don't silently accept) parts outside the band.
- **one palette system used by every animal.** This is the most clearly broken constant today, and there are in fact **three competing palette mechanisms** in the shipped code: (1) literal `"primary"`/`"accent"` attribute values, which are the only thing `hybrid.ts`'s `colourize()` rewrites; (2) `var(--primary,#hex)` CSS-custom-property forms with baked fallbacks — the committed tiger carries exactly two of these per part, and `colourize()` does **not** touch them, so their recolouring silently depends on whether CSS variables are set at render time; and (3) **27 distinct raw hexes** that nothing recolours, ever. `promoteDominantFillToPrimary` promotes exactly *one* fill per part (nearly cosmetic). Net effect: in a hybrid, almost all of a part's colour is permanent species colour. Finish the half-built system by inverting it: define a **fixed token ramp** — `primary`, `accent`, plus a small closed set of *derived* steps (e.g. `primary-light`, `primary-dark`, `accent-dark`, one fixed near-black outline, one fixed off-white) whose values are *computed* from primary/accent at render time, identically for every species — and make `validateAnimalDraft` **reject any raw hex fill/stroke** in part SVGs. This needs a matching small edit where tokens are substituted (`hybrid.ts` `colourize()` and the preview builders) to also resolve the derived steps. Do not let animals declare their own ramp — a per-animal "declared ramp" just reintroduces 27 hexes with extra steps. And the recolor policy is **decided: hybrids keep the single recipe palette** (current `colourize()` behaviour, extended to the derived steps) rather than preserving per-part species palettes — one palette is what makes a frankenstein read as one creature.
- **one detail-density target.** The tiger is the *over*-detailed end — 80 elements and hundreds of nodes blows the old-phone budget and drives the long-output quality decay from section 4. Check element-count-per-part sits in a band: too few reads as a generic Version-B blob, too many is the tiger's problem. **Decided bands, with the tiger (head 27, body 24, legs 10–11, tail 8) as the approximate ceiling: head 8–28, body 8–26, each leg set 5–14, tail 3–10 visible elements.** Sanity-check these against the first N=4 run and tighten if the model reliably lands mid-band.

The constants' values are decided above (mined from the committed tiger and hippo); your job is the exact check to add for each in `validateAnimalDraft` and the precise token-substitution edit. This is four small additions to an existing validator (plus one token-resolution edit in `hybrid.ts`/`preview.ts`), not a new subsystem.

| 50% good | 15% | **85%** |
| 30% good | 1% | **40%** |

- **Reference-image fidelity path** — the repo has a large `referenceAnalysis` / `referenceFeatures` / `paletteSwatches` / match-vs-inspire system across `server.ts`, `validation.ts` and `normalize.ts`. **My lean is to cut it from Stage 1** (text prompts like "a bear" are enough to test whether the game is fun, and this machinery is a major source of validator and prompt complexity). - **In-app model selector (multi-provider) — HIGH PRIORITY, wanted now.** Make the LLM model choosable from the app UI for *every* AI call — animal generation, prompt auto-infill (`populateGuidedBrief`), visual review and repair — instead of being pinned by env at server start. Offer **Gemini in two connection modes**: a direct Google API key (`GEMINI_API_KEY` in `.env`) *and* via **CLIProxyAPI**, plus any other proxy-served models (gpt-5.6-sol, Claude, …). - **Automated vision-based selection** — contact sheets ranked by a multimodal call instead of by me. Trigger: roster growth past ~20 animals making manual picking the bottleneck.
- **Blind identification test** — render to PNG, ask a context-free model "what animal is this?" Note my concern: vision models are generous guessers and pass generic output while failing good stylised art. Say how you'd calibrate it (e.g. against the committed tiger/parametric-hippo pair as known-good/known-bad) before trusting it as a gate.
- **Distinctive-features contract** — the repo has a version of this (`referenceFeatures` + required-group geometry checks in `validation.ts`). It verifies presence and labelling, not shape — a correctly-named blob passes. Say whether it's worth keeping at all and what would strengthen it.
- **Additional anatomy templates** — bird, serpentine, amphibian. Note the package layer **already ships bird/serpentine/scorpion**; Stage-1 *generation* can still target quadruped only. Reconcile.
- **Alternative architectures** — armature-guided freehand with the guide passed as an image; or whole-animal silhouette generation then deterministic cutting into five parts. Say which you'd explore first if Stage 1 quality proves insufficient.
- **Re-enabling automatic repair** — only if select-per-slot proves insufficient. What metric would tell me that?
